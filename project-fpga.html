FPGA Peak Detector — VHDL Digital Design on Artix-7

FPGA-based peak detection system implemented in VHDL on a Digilent CMOD A7 (Artix-7) board. 100 MHz system clock · UART / RS-232 link · command processor FSM · data consumer with two-phase handshake · signed/unsigned peak detection. 基于 UART 命令交互的 FPGA 峰值检测系统， 完整实现命令解析、数据采集、峰值判定与回显的硬件全链路。

// Overview

Designed and implemented a complete peak detection system in VHDL. The full system integrates a peak detector, a data source (data generator with 500-byte sequence), and UART communication links — all implemented in VHDL on a Digilent CMOD A7 board (Xilinx Artix-7, 100 MHz system clock generated from the 12 MHz on-board clock via a clock conditioning IP).

The user types commands into a PuTTY VT100 terminal; keystrokes are sent through the UART (RS-232) link to the FPGA. The system processes a payload stream, identifies the peak byte with respect to signed/unsigned interpretation, and reports it along with the surrounding bytes and index — output back to the terminal via UART TX.

独立完成的 FPGA 工程：在 CMOD A7 (Artix-7) 上以 VHDL 实现峰值检测系统。 PC 终端 (PuTTY) 通过 UART 发送指令 → FPGA 解析命令、两相握手式采集数据、 检测峰值字节 → 经 UART 回传结果。支持 signed/unsigned 两种字节解释模式。

// Functional Specifications

The system is controlled purely through the terminal interface. Every keystroke is echoed, and valid commands trigger specific behaviours:

Command Description
aNNN / ANNN Start command to process NNN bytes (000–999). Each byte is printed to the terminal in hexadecimal, separated by spaces (e.g. FF A9).
p / P Print the peak byte in hexadecimal, followed by a space and its index in decimal (e.g. FD 197).
l / L Print 7 bytes in hexadecimal: 3 preceding the peak + the peak + 3 following (e.g. 09 FA A0 FD BC 10 DE).
BTN1 (push button) Synchronous reset — halts any active processing and returns the system to its initial state.

Edge cases are handled explicitly: if the peak sits near the start/end of the requested window (fewer than 3 valid bytes on either side), the system still prints all 7 bytes — out-of-range entries are simply disregarded, as the index from the P command disambiguates valid data. If multiple peaks occur, the first is retained.

The three supplied modules (UART RX, UART TX, Data Generator) are used without modification; the custom logic — Command Processor and Data Consumer — wraps around them to form the complete peak detection system.

// UART Communication — RS-232

The host PC and FPGA communicate over a UART / RS-232 serial link through the CMOD A7's mini-USB port. The UART_RX_CTRL module captures each received byte and provides it on 8 parallel lines with a valid pulse; the UART_TX_CTRL module serialises 8-bit data for transmission. Terminal echo is implemented by routing every received character straight back to TX.

New-lines are emitted as a two-byte sequence \n + \r (line feed + carriage return) to correctly position the VT100 cursor at the start of a new line.

// Command Processor — FSM Design

The command processor is a finite state machine that parses the incoming byte stream. Command validation follows the spec: a start command is any 'A'/'a' immediately followed by exactly 3 decimal digits — so "hjhgjga945" is valid, while "A56k7" and "a55" are rejected. 

-- VHDL · command processor FSM (skeleton)
type state_t is (IDLE, GOT_A, GOT_D1, GOT_D2, RUN, PRINT_READY);
signal state : state_t;

case state is
  when IDLE =>
    if rx_data = "A" or rx_data = "a" then
      state <= GOT_A;               -- 'A' seen, expect digit #1
    elsif rx_data = "P" or rx_data = "p" then
      -- latch peak + index → TX
    elsif rx_data = "L" or rx_data = "l" then
      -- latch peak neighbourhood (7 bytes) → TX
    end if;
  when GOT_A => ...                 -- digit 1 (000–999)
  when GOT_D1 => ...                -- digit 2
  when GOT_D2 => ...                -- digit 3 → start data run
  when RUN => ...                   -- consume N bytes
  when PRINT_READY => ...           -- wait for P / L
end case;

On a valid aNNN, the FSM transitions to RUN, clocks exactly NNN bytes from the data generator (each immediately printed in hex), then settles into PRINT_READY where P/L queries are served.

// Data Consumer — Two-Phase Handshake

The data generator supplies a 500-byte sequence one byte at a time under a two-phase handshake: the consumer requests a new byte by toggling req; the generator responds by placing the next byte on the data lines and toggling data_valid. The data consumer latches the byte on each valid edge, streams it to UART TX for hex display, and simultaneously updates its internal peak tracking: 

-- VHDL · peak tracking (unsigned flavour)
if data_valid'event then          -- toggle detected
  if data > peak_value then      -- strict > keeps FIRST peak
    peak_value <= data;
    peak_index <= index_cnt;
  end if;
  -- shift neighbourhood: b0←b1, b1←b2, b2←peak_prev ...
  index_cnt <= index_cnt + 1;
end if;

Only a strictly greater comparison is used, so the first occurrence of a repeated maximum is the one retained — exactly the behaviour the specification requires. A ring of registers keeps the 3 preceding bytes, the peak, and latches the 3 following bytes to serve the L command.

// Signed vs Unsigned Interpretation

The byte's interpretation (which byte "wins" as the peak) is determined by the group number. Two full implementations were synthesised:

Flavour Comparison Range Key source files
Unsigned 8-bit unsigned magnitude 0 – 255 dataConsume_synthesised_unsigned.vhd
Signed Two's-complement signed −128 – +127 dataConsume_synthesised_signed.vhd

Both variants share the same top-level structure (top.vhd, cmdProc, dataGen) and were each synthesised, placed, and routed into a .bit file for on-board verification.

// Verification — Simulation & On-Board

Rapid verification was driven by dedicated testbenches:

Testbench Scope
tb_UART.vhd UART RX/TX byte-level exchange, baud timing, echo path
tb_dataGenConsume_signed/unsigned.vhd Two-phase handshake + peak tracking for the full 500-byte sequence
tb_dataConsume_signed/unsigned.vhd Data consumer standalone: peak, index, ±3 neighbourhood registers
tb_CmdProcessor_Interim.vhd Command FSM: valid/invalid command strings, P/L after run

Final validation was performed with the generated bitstream programmed onto the CMOD A7 via Vivado 2022.2 Hardware Manager, interacting through a PuTTY terminal — covering all commands, various sequence lengths, and edge cases. Full details are in the accompanying report (digital_report.pdf).
