裸机 vs FreeRTOS：我用 6 个任务重写了避障机器人

Deng Wenbo · RTOS · Embedded · ~7 min read

同一个机器人，我先用裸机"while(1) + 中断"写完，再用 FreeRTOS 的 6 个任务重写了一遍。这篇记录两种架构的取舍、Mutex 优先级反转的坑，以及硬件中断向量寄存器（P4IV）的正确用法。

为什么要把同一个项目写两遍？

基于 ARM Cortex-M4F (MSP432P401R, 48MHz) 的自主避障机器人：6 个碰撞开关、 2 路电机软件 PWM、蜂鸣器音乐、RGB LED 状态显示。Part 1 用裸机中断驱动实现； Part 2 换成 FreeRTOS 6 任务并发调度。

写两遍不是重复劳动——它是理解"调度器解决了什么、又引入了什么"最直接的方式： 裸机的简单直接 vs RTOS 的可扩展性，本质上是复杂度管理的取舍。

Part 1：裸机架构 — 超级循环 + 中断

/* 裸机骨架：main loop 做非实时任务，ISR 抢占处理碰撞 */
while (1) {
    Check_Buttons();      // 慢速轮询：按钮、音乐、LED
    Update_Motor();       // 软件 PWM 占空比更新
    Play_Music_Step();    // 蜂鸣器节拍推进
}

// Port4 下降沿中断：6 个碰撞开关共用一条 IRQ38
void PORT4_IRQHandler(void) {
    status = P4->IV;      // 硬件自动仲裁 + 清中断标志
    switch(status) {
        case 0x02: Bump1_Action(); break;
        case 0x06: Bump2_Action(); break;
        /* ... 0x08 / 0x0C / 0x0E / 0x10 → Bump3..6 */
    }
}

坑 1：P4IV 的中断向量值不是"猜"出来的

初版代码里我给 P4->IV 写错了 case 值——因为想当然认为 6 个引脚对应 0x01..0x06。查 MSP432 手册才发现规律： P4IV = 2 × (pin + 1)，即 Pin0→0x02、Pin1→0x04、Pin2→0x06 … Pin7→0x10。

P4->IV 的价值在于：多个开关同时触发时, 硬件自动返回最高优先级待处理引脚，并自动清除对应的 IFG 标志——比在 ISR 里逐个读 PFIN 判断高效且不会漏事件。

裸机的局限：实时性只是"看起来"实时

裸机里碰撞响应是 ISR 立即抢占，延迟确实低。但当系统膨胀到 "避障 + 音乐 + 按键 + LED + 电机 + 显示"多路并发时，main loop 越来越长， 每个功能的响应时间开始互相依赖——可预测性丢失是裸机最大的隐性成本。

Part 2：FreeRTOS 架构 — 6 任务并发调度

/* 6 个任务 · 5 级优先级 · 1ms tick（1000Hz） */
- taskT             (prio 2): 总控，SW2 挂起/恢复所有任务
- taskBumpSwitch    (prio 1): 碰撞检测（中断置 flag → 任务响应）
- taskdcMotor       (prio 1): 电机方向 + 软件 PWM
- taskMusic         (prio 1): 蜂鸣器音乐播放
- taskInput         (prio 1): 按键输入
- taskDisplayOutputLED (prio 1): RGB LED 状态显示

碰撞开关的中断里不再做业务逻辑，只负责唤醒任务 （xSemaphoreGiveFromISR），实际的避障决策交给 taskBumpSwitch。中断变短、任务职责单一，这就是 RTOS 带来的关注点分离。

坑 2：优先级反转与 Mutex 的优先级继承

三个任务（taskBumpSwitch / taskdcMotor / taskDisplayOutputLED）都要访问全局状态 bumpSwitch_status。初版用二进制信号量保护，结果出现： 低优先级任务持有锁 → 高优先级任务被阻塞 → 中优先级任务插队 → 高优先级任务饿死。 

// 错误：BinSemaphore 只保证互斥，不解决优先级反转
SemaphoreHandle_t xBumpMutex = xSemaphoreCreateMutex();  // 用 Mutex！

if( xSemaphoreTake(xBumpMutex, portMAX_DELAY) ) {
    bumpSwitch_status = Bump_Read_Input();
    xSemaphoreGive(xBumpMutex);
}
/* Mutex 的优先级继承：持锁期间临时抬升持锁者优先级，
   阻断中优先级任务插队 → 收敛为可控的等待时间 */

Mutex（互斥量）与二进制信号量的关键区别正是"优先级继承"： 当高优先级任务因等锁被阻塞时，锁持有者的优先级被临时提升到与等待者相同， 从而不被中优先级任务抢占。这是 FreeRTOS Mutex 内置的行为， 也是面试最常被追问的 RTOS 概念之一。

坑 3：vTaskSuspend 传错参数

初版代码写的是 vTaskSuspend(taskMusic)——传了函数指针， 编译期完全不报错，运行时任你怎么按 SW2 任务纹丝不动。 正确做法是传 TaskHandle_t，创建任务时保存句柄： 

TaskHandle_t xTaskMusicHandle;

xTaskCreate(TaskMusic, "Music", stackSize, NULL, 1, &xTaskMusicHandle);
// ...
vTaskSuspend(xTaskMusicHandle);   // 正确：句柄，不是函数名

裸机 vs RTOS：一张决策表

Aspect Part 1: Bare Metal Part 2: FreeRTOS
Program Structure while(1) + ISR Tasks + Scheduler
Concurrency ISR preempts main loop Priority + time-slice switching
Responsiveness Immediate (ISR) Depends on priority/scheduling
Shared Data volatile keyword Mutex protection + priority inheritance
Complexity Low Higher (race / deadlock / inversion)
Scalability Degrades as features grow Add tasks without hobbling main loop

核心结论：系统功能少 → 裸机更优（代码可读、延迟确定）；并发功能多 → RTOS 的 任务抽象和确定性调度收益远大于同步成本。 对硬件工程师而言，两种都该会， 而判断"什么时候该上 RTOS"本身就是工程经验的一部分。

经验总结

  1. P4IV 之类的硬件向量寄存器一定查手册，别靠猜——它是"多引脚共享中断"的标准解法
  2. 共享数据用 Mutex 而非常规信号量，优先级继承能规避反转导致的饿死
  3. RTOS 里中断只负责"唤醒"，业务放任务里——ISR 越短越不容易丢事件
  4. 传 TaskHandle_t 而不是函数名，这类错误静默发生，调试周期极长
  5. 选择架构时先数"并发源"：超过 3 个实时事件源，就该考虑 RTOS
