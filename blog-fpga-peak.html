从 VHDL 到硬件：在 Artix-7 上用状态机实现峰值检测

Deng Wenbo · FPGA · VHDL · Digital Logic · ~7 min read

在一个 100MHz 的 Artix-7 上，用 VHDL 写一个「终端命令 → 数据采集 → 峰值判定 → 串口回显」的完整硬件系统。这篇记录命令解析 FSM 的设计、两相握手协议的细节，以及 signed/unsigned 两种字节解释的实现与验证。

系统要做什么？

用户在 PuTTY (VT100) 终端输入命令，通过 UART / RS-232 发给 Digilent CMOD A7 （Xilinx Artix-7，板载 12MHz 晶振经 MMCM/PLL 倍频到 100MHz 系统时钟）。 FPGA 解析命令、按两相握手从数据源取数、判定峰值字节，再把结果回传终端。 

/* 功能规格（来自 ECAD 设计规范） */
aNNN / ANNN : 启动处理 NNN 个字节 (000–999)，逐字节十六进制打印
P / p       : 打印峰值字节 + 十进制索引（如 "FD 197"）
L / l       : 打印峰值 ±3 邻居共 7 字节
BTN1        : 同步复位，终止一切处理
// signed/unsigned 两种模式各自独立，谁"更大"谁赢

架构：三段式硬件流水

/* FPGA 顶层结构 — 复用 UART + 数据源，自研命令与消费逻辑 */
PC/PuTTY ◄──UART Rx/Tx──► Command Processor (FSM)
                            │ start / count / req
                            ▼
                         Data Consumer
                            │ req ─┐  ▲ data_valid
                            ▼      └──┤
                         Data Generator (500-byte 序列)

三个给定模块（UART RX、UART TX、数据生成器）原封不动接入； 真正需要设计的是命令处理器（FSM）和数据消费者。 这种"外围给定、核心自研"的模式非常接近真实企业里的模块化开发。

核心 1：命令处理器 — 有限状态机

命令校验遵循规范：任何 'A'/'a' 后紧跟恰好 3 位十进制数字 才算有效启动命令。因此 "hjhgjga945" 合法， 而 "A56k7"、"a55" 必须拒绝。 

-- VHDL · 命令处理器 FSM 骨架
type state_t is (IDLE, GOT_A, GOT_D1, GOT_D2, RUN, PRINT_READY);
signal state : state_t;

case state is
  when IDLE =>
    if rx_data = "A" or rx_data = "a" then
      state <= GOT_A;               -- 见到 'A'，等待第 1 位数字
    elsif rx_data = "P" or rx_data = "p" then
      -- 锁存峰值 + 索引 → TX
    elsif rx_data = "L" or rx_data = "l" then
      -- 锁存峰值邻域 7 字节 → TX
    end if;
  when GOT_A  => ...   -- 第 1 位数字 (000–999)
  when GOT_D1 => ...   -- 第 2 位数字
  when GOT_D2 => ...   -- 第 3 位数字 → 启动数据运行
  when RUN => ...      -- 消费 N 个字节
  when PRINT_READY => ...   -- 等待 P / L 查询
end case;

合法 aNNN 使 FSM 进入 RUN， 从数据源精确时钟 NNN 个字节（每个立即以十六进制打印）， 然后进入 PRINT_READY 等待 P/L。

核心 2：数据消费者 — 两相握手

数据生成器每次只吐 1 个字节，通过两相握手同步： 消费者翻转 req 请求新字节 → 生成器放数据并翻转 data_valid → 消费者在有效沿锁存。 

-- VHDL · 峰值跟踪（unsigned 版本）
if data_valid'event then          -- 检测翻转沿
  if data > peak_value then      -- 严格大于 → 保留第一个峰值
    peak_value <= data;
    peak_index <= index_cnt;
  end if;
  -- 邻域寄存器链：b0←b1, b1←b2, b2←peak_prev ...
  index_cnt <= index_cnt + 1;
end if;

为什么"大于"必须严格？

规范要求多个相同最大值时保留第一个。用 data > peak （而非 >=）后，重复的最大值不会覆盖已记录的峰值， 恰好满足"FIRST peak retained"。这类边界语义是硬件设计与上层软件最大的差异—— 一个比较器的符号都可能改变系统行为。

邻域 7 字节怎么来？

一组长度为 6 的移位寄存器链持续滚动：锁存最近 6 个字节。检测到峰值时， 前 3 个（链中段的旧数据）就是 peak−3..peak−1， 峰值后每来一个字节再推入链尾，凑齐后 3 个。若窗口越界（峰值靠近序列头尾）， 规范允许直接打印——由 P 命令的索引消歧。

signed vs unsigned：同一套逻辑，两种世界观

Flavour Comparison Range
Unsigned 8-bit magnitude 0 – 255
Signed Two's-complement −128 – +127

同一个设计参数化出两套实现，各自独立综合、布线、生成 .bit 并上板验证。 这让我意识到：硬件的"数据类型"是设计决策，不是编译器的事——选错解释方式，0xFF 到底是 255 还是 −1，峰值结果完全不同。

验证策略：仿真先行，上板收尾

Testbench Scope
tb_UART.vhd UART 字节级收发、波特率时序、回显路径
tb_dataGenConsume_*.vhd 两相握手 + 完整 500 字节序列的峰值跟踪
tb_dataConsume_*.vhd 消费模块：峰值、索引、±3 邻域寄存器
tb_CmdProcessor_Interim.vhd 命令 FSM：合法/非法字符串、RUN 后 P/L

最终通过 Vivado 2022.2 Hardware Manager 把 bitstream 烧进 CMOD A7，用 PuTTY 终端逐一验证所有命令、多种序列长度和边界情况。 仿真无法替代上板——时序收敛、引脚约束、真实波特率下的稳定收发，只有硬件会告诉你。

经验总结

  1. FSM 是数字控制的核心武器——复杂命令解析拆成状态转移，可读且可仿真验证
  2. 两相握手天然跨时钟域安全，是模块间数据同步的教科书方案
  3. 比较器的"严格大于"是一种语义选择，直接影响边界行为（FIRST peak）
  4. signed/unsigned 是设计问题不是类型问题——同样的比特流，解释方式决定一切
  5. 仿真 + 上板双验证缺一不可：testbench 保证逻辑正确，bitstream 保证物理成立
